# Звіт про виконання ЛР1: Вимоги та проєктування з AI-асистентом

**Проєкт:** VerbaDesk (адаптація Mini Issue Tracker для бюро перекладів)
**Команда:** Олександра Нікітіна, Ярослава Пащенко
**Версія/Тег:** `lab01-spec`

## 1. Мета і коротко виконана робота
**Мета:** Навчитися використовувати AI-асистента для системного аналізу, уточнення розмитих вимог замовника та проєктування однозначної специфікації, архітектури і API-контракту.
**Виконано:** 
Перетворено неструктурований запит на переклад у строгий контракт даних. Визначено 7 User Stories, розроблено матрицю станів 4х4, спроєктовано 9 REST API ендпоінтів та C4-архітектуру на базі FastAPI + SQLite. Складено матрицю простежуваності (Traceability) у форматі CSV.

## 2. Власний аналіз до звернення до АІ
Перед використанням ШІ ми самостійно проаналізували вихідний запит замовника та виявили такі неоднозначності:
* **Ярослава:** «Користувач створює заявку...» — Хто такий "користувач"? Це будь-який клієнт з інтернету, чи це менеджер бюро реєструє запит вручну?
* **Ярослава:** «Команда переглядає запити, призначає перекладача...» — Скільки людей у команді і чи є поділ на ролі? Чи може перекладач сам призначити заявку на себе?
* **Олександра:** «змінює статус...» — Які взагалі існують статуси? Чи можна перевести статус із "Закрито" назад у "Відкрито", якщо клієнт знайшов помилку?
* **Олександра:** «швидко бачити важливі відкриті запити...» — Що саме робить запит "важливим"? Це якийсь окремий статус чи просто високий пріоритет?
*Висновок:* Порівнявши ці питання з погодженою специфікацією VerbaDesk, ми побачили, що ролі, пріоритети та статуси були визначені замовником пізніше, що зняло ці питання.

## 3. Ключові рішення або уточнення вимог
Під час аналізу вихідного запиту за допомогою ШІ та командного обговорення було виявлено та формалізовано такі критичні правила (Decision Log):
*   **D-01 (Role-Based Access):** Жорстко розмежовано права. Менеджер має ексклюзивне право змінювати `Priority` та `Assignee`, але не може змінювати `Status` (це робить лише поточний виконавець).
*   **D-03 (Поведінка Closed):** Зафіксовано, що заявка зі статусом `CLOSED` стає read-only для всіх текстових полів та статусів (заборонено будь-які переходи), але система дозволяє додавати до неї нові коментарі для збереження історії обговорень.
*   **D-05 (Атомарність PATCH):** Визначено, що при частковому оновленні (PATCH), якщо хоча б одне передане поле є невалідним або забороненим для ролі, весь запит відхиляється атомарно (422 або 403), і жодні зміни не зберігаються.
*   **D-06 (Зміна вихідної вимоги щодо Опису):** У базовій методичці поле Description було необов'язковим. Команда прийняла свідоме, погоджене рішення змінити цю вимогу і зробити поле обов'язковим (мінімум 1 символ). Це зроблено для того, щоб унеможливити створення "порожніх" заявок, які не несуть контексту для перекладача.

## 4. Показові випадки використання AI з перевіркою результату
1.  **Пошук неоднозначностей (Крок 2):** Замість відкритого запиту ми використали жорсткий системний промпт (заборонили вигадувати нові функції, попросили перевірити всі 16 комбінацій станів). *Результат:* ШІ допоміг формалізувати заданий факт (що повторне встановлення вже поточного статусу не є помилкою) у вигляді повної матриці переходів та визначив коректний HTTP-код (200 OK). *Перевірка:* Звірили з вихідними правилами. Прийняли технічну формалізацію ШІ, додавши правило D-02 (ідемпотентність: 200 OK без фактичних змін у базі).
2.  **Генерація Traceability Matrix (Крок 9):** Ми задали ШІ роль QA-інженера та наказали вивести дані у форматі CSV для машинного парсингу. *Результат:* Ідеальна генерація зв'язків між FR, User Stories, API та назвами майбутніх тестів.

## 7. Короткі висновки
Штучний інтелект є потужним інструментом для виявлення "сліпих зон" у вимогах (edge cases) та рутинної генерації структур (таблиць, Markdown, CSV). Однак ШІ часто схильний уникати прийняття остаточних бізнес-рішень. Метод *Human-in-the-loop* (людина в циклі) довів свою ефективність: команда повинна самостійно затверджувати правила доступу, архітектурні обмеження (SQLite замість важких БД) та контролювати відсутність галюцинацій.
