# VerbaDesk: Вимоги та бізнес-правила (Requirements Specification)

## 1. Функціональні вимоги (Functional Requirements - FR)
* **FR-01:** Створення заявки на переклад із обов'язковими назвою та описом.
* **FR-02:** Перегляд списку заявок та фільтрація за статусом і пріоритетом (разом працюють як логічне AND).
* **FR-03:** Редагування заявки (часткове оновлення текстових полів та пріоритету залежно від ролі).
* **FR-04:** Керування статусом заявки (суворо за матрицею переходів).
* **FR-05:** Призначення та зняття відповідального перекладача (Assignee).
* **FR-06:** Додавання та перегляд коментарів до заявки.
* **FR-07:** Збереження даних (SQLite) та валідація вхідних запитів із забезпеченням атомарності.
* **FR-08:** (Поза обсягом MVP, для ЛР4) AI-рекомендація категорії та пріоритету.

## 2. Нефункціональні вимоги (Non-Functional Requirements - NFR)
* **NFR-01 (Швидкодія):** Час відповіді API на запити читання (GET) та часткового оновлення (PATCH) не повинен перевищувати 1 секунди при локальному тестуванні.
* **NFR-02 (Збереження):** Дані зберігаються локально у файлі SQLite (`database.db`). Після перезапуску сервера всі раніше створені заявки, коментарі та зміни статусів мають бути доступні.
* **NFR-03 (Валідація та помилки):** Система повинна відхиляти будь-які некоректні запити (наприклад, недопустима довжина назви або неправильний тип даних) зі стандартизованою відповіддю HTTP `422 Unprocessable Entity` і зрозумілим повідомленням про помилку.
* **NFR-04 (Ізоляція):** Система повинна підтримувати запуск із тестовою базою даних, що забезпечить незалежне виконання автоматизованих тестів без впливу на основні дані.

## 3. Контракт даних (Data Model)
Модель `TranslationRequest` (Заявка на переклад):

| Поле | Тип | Обов'язкове (Create) | Типове значення | Валідація / Обмеження | Зміна після створення |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | Integer | Ні (генерує система) | - | Унікальний ідентифікатор | Заборонено |
| `title` | String | Так | - | Від 3 до 120 символів після `strip()` | Дозволено (не CLOSED) |
| `description` | String | Так | - | Мінімум 1 символ. Може містити текст та/або URL | Дозволено (не CLOSED) |
| `status` | Enum | Ні | `OPEN` | `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED` | Дозволено (Current Assignee) |
| `priority` | Enum | Ні | `null` | `Low`, `Normal`, `High`, `Critical`, або `null` (Not Set) | Дозволено (лише Manager) |
| `assignee_id`| Integer | Ні | `null` | ID існуючого Translator (1 або 2) або `null` | Дозволено (лише Manager) |
| `author_id` | Integer | Ні (з сесії) | Сurrent User | ID автентифікованого користувача | Заборонено |
| `created_at` | DateTime| Ні (генерує система) | Час сервера(UTC) | ISO 8601 формат | Заборонено |

## 4. Журнал рішень та бізнес-правила (Decision Log)

### D-01: Матриця прав доступу
Будь-який автентифікований член команди може створювати, переглядати заявки, додавати коментарі та редагувати `Title` і `Description` (якщо заявка не CLOSED).
Специфічні обмеження:
*   **Призначення (Assignee):** Змінювати/знімати може виключно `Manager`.
*   **Пріоритет (Priority):** Команда може обговорювати пріоритет у коментарях, але змінювати поле може виключно `Manager`.
*   **Статус (Status):** Змінювати статус може **лише поточний відповідальний перекладач** (Current Assignee). Якщо Assignee не призначений, зміна статусу відхиляється (`409 Conflict`).

### D-02: Матриця переходів станів та ідемпотентність
Повторне передавання поточного статусу є успішною операцією (`200 OK`), але не створює фактичних змін. 

| Поточний ↓ / Новий → | `OPEN` | `IN_PROGRESS` | `RESOLVED` | `CLOSED` |
| :--- | :--- | :--- | :--- | :--- |
| `OPEN` | 200 OK (без змін) | Дозволено | 409 Conflict | Дозволено |
| `IN_PROGRESS` | 409 Conflict | 200 OK (без змін) | Дозволено | 409 Conflict |
| `RESOLVED` | 409 Conflict | Дозволено | 200 OK (без змін) | Дозволено |
| `CLOSED` | 409 Conflict | 409 Conflict | 409 Conflict | 200 OK (без змін) |

### D-03: Поведінка статусу CLOSED
Заявка `CLOSED` доступна виключно для читання основних даних. Будь-які зміни (Title, Description, Status, Priority, Assignee) відхиляються з `409 Conflict`. Проте дозволено додавати нові коментарі до закритої заявки.

### D-04: Priority "Not Set" та "Important Requests"
Пріоритет "Not Set" технічно зберігається як `null`. Заявка вважається важливою (`Important`) виключно якщо її `priority` = `High` або `Critical`, А ТАКОЖ її `status` не дорівнює `CLOSED` (тобто `OPEN`, `IN_PROGRESS`, `RESOLVED`).

### D-05: Часткове оновлення (PATCH) та Атомарність
Якщо клієнт не передає поле у PATCH-запиті, воно залишається без змін. Якщо поле передається як `null` (і це дозволено контрактом, напр., для `priority` або `assignee_id`), значення скидається. Якщо запит містить хоча б одне некоректне поле (або спробу змінити заборонене для ролі поле), весь запит відхиляється атомарно, жодні зміни не зберігаються.

## 5. User Stories та Acceptance Criteria (Given-When-Then)

### US-01 (FR-01): Створення заявки
*Як автентифікований член команди, я хочу створити заявку з назвою та описом, щоб зафіксувати нову задачу.*
*   **AC-01.1 (Позитивний):** Given користувач передає коректні `Title` та `Description` (не порожні), When він надсилає запит, Then система створює заявку, встановлює `Status = OPEN`, `Priority = null`, записує автора і повертає `201 Created`.
*   **AC-01.2 (Негативний):** Given користувач не передає `Description` або передає порожній рядок, When він надсилає запит, Then система відхиляє його і повертає `422 Unprocessable Entity`.

### US-02 (FR-02): Перегляд і фільтрація
*Як член команди, я хочу переглядати і фільтрувати заявки, щоб швидко знаходити потрібні тексти.*
*   **AC-02.1 (Фільтр AND):** Given у базі є різні заявки, When користувач надсилає запит із фільтрами `status=OPEN` та `priority=High`, Then система повертає лише ті заявки, що відповідають обом умовам одночасно.
*   **AC-02.2 (Порожній результат):** Given жодна заявка не відповідає фільтрам, When користувач робить запит, Then система повертає успішний порожній список `[]` (`200 OK`), а не помилку.

### US-03 (FR-03): Редагування назви та опису
*Як член команди, я хочу змінювати текстові дані заявки, щоб виправляти помилки або додавати посилання.*
*   **AC-03.1 (Атомарність):** Given заявка `OPEN`, When користувач надсилає коректний `Title` та некоректний (порожній) `Description` в одному запиті, Then система повертає `422 Unprocessable Entity` і не зберігає жодних змін (навіть коректного Title).
*   **AC-03.2 (Захист CLOSED):** Given заявка `CLOSED`, When користувач намагається оновити `Title`, Then система відхиляє запит і повертає `409 Conflict`.

### US-04 (FR-04): Керування статусом
*Як відповідальний перекладач, я хочу змінювати статус своєї заявки, щоб команда бачила прогрес.*
*   **AC-04.1 (Успішний перехід):** Given заявка `OPEN` і користувач є її `Assignee`, When він передає новий статус `IN_PROGRESS`, Then система оновлює статус і повертає `200 OK`.
*   **AC-04.2 (Немає виконавця):** Given заявка не має призначеного перекладача (`assignee_id = null`), When будь-який користувач намагається змінити її статус на `IN_PROGRESS`, Then система повертає `409 Conflict`.

### US-05 (FR-05): Керування пріоритетом та виконавцем (Права Менеджера)
*Як Менеджер, я хочу встановлювати пріоритет і виконавця, щоб координувати роботу бюро.*
*   **AC-05.1 (Позитивний):** Given користувач має роль `Manager`, When він передає `Priority = High` та `assignee_id = 2` для незакритої заявки, Then система успішно зберігає дані (`200 OK`).
*   **AC-05.2 (Обмеження ролі):** Given користувач має роль `Translator`, When він намагається змінити `Priority` або `assignee_id`, Then система відхиляє запит із `403 Forbidden` і залишає дані без змін.

### US-06 (FR-06): Додавання коментарів
*Як член команди, я хочу додавати коментарі до заявки, щоб обговорювати переклад.*
*   **AC-06.1 (Коментування CLOSED):** Given заявка має статус `CLOSED`, When користувач додає валідний коментар, Then система приймає його і повертає `201 Created`.
*   **AC-06.2 (Негативний):** Given текст коментаря порожній, When користувач надсилає запит, Then система повертає `422 Unprocessable Entity`.

### US-07 (FR-07): Невідома заявка
*Як член команди, я хочу отримувати зрозумілу відповідь, якщо запитую неіснуючу заявку.*
*   **AC-07.1:** Given у базі немає заявки з ID 999, When користувач запитує `GET /issues/999` або `PATCH /issues/999`, Then API повертає `404 Not Found`.

### US-08 (FR-08): AI-рекомендація (Майбутня фіча)
*Як член команди, я хочу отримувати AI-рекомендації, щоб швидше визначати категорію тексту.*
*   **Примітка:** Знаходиться поза обсягом MVP (не реалізується в ЛР1-ЛР3). AI-дія має виключно рекомендаційний характер.
